AWS architecture

Proposed reference design

Two ways into an environment: deploy through GitHub Actions, or use its HTTP(S) endpoints.

1. Deploy / change

Developer or agent triggers GitHub Actions. Actions uses the target environment's IAM role to deploy code and infrastructure.

Developer / agent → GitHub Actions → selected environment

2. Use / test

A browser, API client or agent's HTTP MCP client calls the target environment's webpage, API or MCP server. Responses return to the caller.

Browser / API / MCP client ⇄ environment HTTP(S) endpoint
AI context & responses Code, skills & deployment HTTP(S) requests / responses & internal data access

What crosses the boundary

Code & artifacts
Local commits reach GitHub through review. The normal path is Actions deployment to NonProd (Dev), followed by promotion of the tested revision to Prod after validation and approval. Sandbox is optional, for concept testing only. Each target uses its own OIDC role, S3 deployment bucket and SAM / CloudFormation stack. Promote code revisions, not environment databases.
Skills & AI context
NCI-Skills-Library supplies versioned instructions installed locally and read by the agent. Selected instructions, prompts and code context may reach Copilot's hosted inference. No secrets or production records in prompts. Runtime skill packaging is explicit, not automatic.
Application data
Browsers, API clients and HTTP MCP clients send requests to the selected environment's HTTPS endpoint. In the Lambda-backed example, API Gateway invokes Lambda; Lambda accesses internal stores and returns responses through Gateway. Static websites may instead use CloudFront with an S3 origin, still through HTTP(S). Queues and database access are internal service flows, not additional external entry paths.

Environment access rule

In this design, developers and local agents do not connect directly to AWS databases, S3 buckets, Lambda management APIs or host shells, and do not deploy through a local AWS CLI or the AWS console. Infrastructure changes go through GitHub Actions; application use and testing go through the environment's authenticated HTTP(S) endpoints. Any future administrative exception requires a separately defined access path.

GitHub repository traffic, Copilot inference and Registry metadata fetches remain outside these AWS application boundaries. The two entry paths are an architectural requirement, not a claim that enforcement has already been configured.

NCI-Skills-Registry & its website

NCI-Skills-Registry holds the application inventory, schema and static website. The registry dashboard and application list currently run in the browser from this local server; their JavaScript fetches registry.json from the GitHub main branch over HTTPS. That metadata does not pass through an application API Gateway or Lambda.

AWS hosting for this website is a proposed S3 + CloudFront option, not a confirmed deployment. Registry metadata records application ownership, deployment location and skills used; it is not the application's business-data store. Updates to the Library and Registry should be reviewed independently of application deployments.

Design assumptions: distinct accounts and roles; protected production environment; approved inputs and data handling. These safeguards still require implementation and verification.
